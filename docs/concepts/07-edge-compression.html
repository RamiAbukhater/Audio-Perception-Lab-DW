Quantization, pruning, and edge benchmarking

A trained PyTorch model stores every weight as a 32-bit float and assumes a laptop-class CPU. An ESP32 has about half a megabyte of RAM and no floating-point vector unit; a Raspberry Pi Pico has 264 KB of RAM and no floating-point hardware at all. This page explains how we shrink a model to fit (8-bit quantization and pruning) and how to measure, honestly, what we gained and what we lost.

The big idea

Neural network weights do not need 32 bits of precision. Most layers work almost as well if each weight is rounded to one of 256 levels and stored as an 8-bit integer. That gives a 4× smaller model, and on hardware with integer instructions it runs several times faster, because integer multiply-accumulates are cheaper than floating-point ones and four times as many values fit in each memory transfer.

Quantization reduces the precision of each number. Pruning removes numbers altogether. Both trade a little accuracy for a lot of efficiency, and the research question in Module 1 is exactly how much accuracy, and whether the loss gets worse in noise.

Three separate budgets matter on a microcontroller:

  • Flash holds the model weights and the program. Weights are read-only, so they live here. An int8 model with 100k parameters needs about 100 KB.
  • RAM holds activations (intermediate feature maps), the audio buffer, and the log-mel front end's working memory. Peak activation memory is usually the binding limit, not weight size. It is set by the largest pair of adjacent feature maps, so early, high-resolution layers dominate.
  • Latency: if the model sees a 1-second window every 0.5 seconds, the full pipeline (front end plus model) must finish in under 0.5 s, and preferably far less to leave the CPU free.

Since we may not have every device on hand, the spec says "simulated hardware constraints": enforce the budgets in software (count parameters and peak activation bytes, cap threads to 1, measure latency on a Raspberry Pi or with ONNX Runtime pinned to one core) and validate on real hardware when we can.

Affine int8 quantization

Map a real value \(r\) to an integer \(q\) with a scale \(s\) (a positive float) and a zero point \(z\) (an integer):

\[ q = \operatorname{clamp}\!\left(\operatorname{round}\!\left(\frac{r}{s}\right) + z,\ q_{\min},\ q_{\max}\right), \qquad \hat r = s\,(q - z). \]

Choose \(s\) and \(z\) so the observed range \([r_{\min}, r_{\max}]\) fills the integer range:

\[ s = \frac{r_{\max} - r_{\min}}{q_{\max} - q_{\min}}, \qquad z = q_{\min} - \operatorname{round}\!\left(\frac{r_{\min}}{s}\right). \]
  • Asymmetric (as above, uint8 0–255) fits skewed ranges well, such as post-ReLU activations, which are never negative.
  • Symmetric (int8 −127 to 127, \(z = 0\), \(s = \max|r| / 127\)) is used for weights, because it makes the integer arithmetic simpler.
  • Per-channel quantization gives each output channel of a conv layer its own scale. Channels have very different ranges, so this is much more accurate than one scale per tensor and is the default for weights.

The rounding error is at most \(s/2\) per value. The enemy is outliers: one huge value stretches the range, increases \(s\), and wastes most of the 256 levels on empty space.

Post-training quantization (PTQ)

PTQ quantizes an already-trained model without retraining. Weights are easy: their ranges are known. Activations depend on the input, so PTQ runs a calibration step: feed a few hundred representative inputs, record the range of every activation with observers, then fix the scales and zero points. Calibration data should look like deployment data, which for Module 1 means including noisy clips, not only clean ones.

If PTQ loses too much accuracy, the next step is quantization-aware training (QAT): simulate the rounding during fine-tuning so the weights learn to tolerate it. Try PTQ first; it is often within a point of float for CNNs like ours.

import copy
import torch
from torch.ao.quantization import get_default_qconfig_mapping
from torch.ao.quantization.quantize_fx import prepare_fx, convert_fx

torch.backends.quantized.engine = "qnnpack"        # ARM-style int8 kernels; use "x86" on Intel desktops
model.eval()
qconfig_mapping = get_default_qconfig_mapping("qnnpack")
example = (torch.randn(1, 1, 64, 201),)

prepared = prepare_fx(copy.deepcopy(model), qconfig_mapping, example)   # inserts observers, folds BN
with torch.no_grad():
    for x, _ in calib_loader:                       # ~100-500 clips, clean AND noisy
        prepared(normalise(frontend(x)))
qmodel = convert_fx(prepared)                       # int8 weights and activations

torch.save(qmodel.state_dict(), "tiny_int8.pt")
  • prepare_fx traces the model, fuses Conv → BatchNorm → ReLU into single ops, and inserts observers after each layer.
  • The calibration loop only runs forward passes; no gradients, no labels.
  • convert_fx replaces observers with quantize/dequantize steps and swaps modules for their int8 versions.
  • Evaluate qmodel on the same SNR sweep as the float model. Report both curves.

PTQ with ONNX Runtime

ONNX is a portable model format. Exporting to ONNX lets you quantize with ONNX Runtime, benchmark on a Raspberry Pi, and convert onward to microcontroller runtimes (for example TFLite Micro via a converter, or ESP-DL).

import numpy as np
import torch
from onnxruntime.quantization import quantize_static, CalibrationDataReader, QuantType, QuantFormat

torch.onnx.export(model.eval(), example, "tiny.onnx",
                  input_names=["logmel"], output_names=["logits"], opset_version=17)

class MelReader(CalibrationDataReader):
    def __init__(self, batches):
        self.it = iter([{"logmel": b.numpy()} for b in batches])
    def get_next(self):
        return next(self.it, None)                  # None tells ORT calibration is done

calib = [normalise(frontend(x[:1])) for x, _ in calib_loader]   # batch size 1, like deployment
quantize_static("tiny.onnx", "tiny_int8.onnx", MelReader(calib),
                quant_format=QuantFormat.QDQ, per_channel=True,
                activation_type=QuantType.QInt8, weight_type=QuantType.QInt8)

For our 18k-parameter TinyAudioNet this takes the file from about 76 KB to about 40 KB. The file shrinks less than 4× because ONNX stores graph structure and per-channel scales too; for larger models the ratio approaches 4×. (Recent PyTorch versions default to a newer exporter; if torch.onnx.export errors, try passing dynamo=False.)

Pruning

Pruning sets weights to zero and, ideally, removes them.

  • Unstructured pruning zeroes individual weights, usually those with the smallest magnitude. You can often prune 50–80% with little loss after a short fine-tune. But a matrix that is 70% zeros is still stored and multiplied densely unless the runtime supports sparse kernels, which microcontroller runtimes generally do not. It saves space only once compressed.
  • Structured pruning removes whole filters or channels. The result is just a smaller dense model, so it saves memory and time on any runtime. It hurts accuracy more per parameter removed.
import torch.nn as nn
import torch.nn.utils.prune as prune

params = [(m, "weight") for m in model.modules() if isinstance(m, (nn.Conv2d, nn.Linear))]
prune.global_unstructured(params, pruning_method=prune.L1Unstructured, amount=0.5)   # 50% smallest |w|
# ... fine-tune a few epochs with the masks in place ...
for m, name in params:
    prune.remove(m, name)                       # make zeros permanent, drop the mask buffers

A typical Module 1 pipeline: train → prune (structured, then fine-tune) → quantize (PTQ, then QAT if needed) → export → benchmark. Evaluate after every stage so you know which step cost what.

Benchmarking latency and memory

import time
import numpy as np
import onnxruntime as ort

opts = ort.SessionOptions()
opts.intra_op_num_threads = 1                   # microcontrollers have one core for us
sess = ort.InferenceSession("tiny_int8.onnx", opts, providers=["CPUExecutionProvider"])
x = {"logmel": np.random.randn(1, 1, 64, 201).astype(np.float32)}

for _ in range(20):                             # warm-up: caches, allocators, lazy init
    sess.run(None, x)
times = []
for _ in range(500):
    t0 = time.perf_counter()
    sess.run(None, x)
    times.append((time.perf_counter() - t0) * 1000)
print(f"p50 {np.percentile(times, 50):.2f} ms   p95 {np.percentile(times, 95):.2f} ms")
  • Batch size 1, always: a device classifies one window at a time.
  • Report percentiles (p50 and p95), not just the mean. Real-time systems fail on the slow runs.
  • Include the front end. On a microcontroller, the FFT and mel filterbank can cost as much as a tiny CNN.
  • Memory: report flash (model file size plus code) and peak RAM. Estimate peak activation memory by summing the bytes of the largest simultaneously alive tensors (hooks on each layer can record output sizes); on device, use the runtime's arena-size report (TFLite Micro's tensor arena, for example).
  • Laptop numbers are not device numbers. Use them for relative comparisons (int8 vs float, pruned vs not), and mark them clearly.

Check your understanding

Q1.Weights range over \([-0.5, 0.5]\). With symmetric int8 (\(q \in [-127, 127]\)), what is the scale, and what does 0.123 become?

\(s = 0.5/127 \approx 0.003937\). \(q = \operatorname{round}(0.123/0.003937) = \operatorname{round}(31.24) = 31\). Dequantized: \(31 \times 0.003937 \approx 0.1220\), an error of 0.001.

Q2.Why use asymmetric quantization for activations after ReLU?

They are never negative. A symmetric scheme would waste half of the 256 levels on negative values that never occur, doubling the step size.

Q3.You prune 70% of weights unstructured and the latency on the ESP32 is unchanged. Why?

The runtime still stores and multiplies dense matrices; the zeros are just zeros. Unstructured sparsity needs sparse kernels or compression to pay off. Structured pruning (removing channels) shrinks the dense computation itself.

Q4.Why should calibration data include noisy clips?

Noise changes activation ranges. If calibration sees only clean audio, the scales are set for clean ranges, and noisy inputs at deployment get clipped at the extremes, adding error exactly where the model is already struggling.

Common mistakes

  • Comparing int8 and float on different test sets or different front ends.
  • Calibrating on the test set. Use training or validation clips.
  • Timing without warm-up, or with many threads, or with batch size 32.
  • Reporting only weight size when peak activation RAM is what does not fit.
  • Forgetting model.eval() before export or calibration, which leaves batch norm in training mode and breaks folding.
  • Assuming unstructured sparsity speeds things up on a microcontroller.
