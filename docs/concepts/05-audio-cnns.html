Training CNNs on spectrograms

Once audio is a log-mel image, we can borrow the most reliable tool in computer vision: the convolutional neural network. This page explains why that works, what is different about spectrograms compared with photos, how to build a network small enough for a microcontroller, and how to train it on UrbanSound8K without fooling yourself.

The big idea

A convolutional layer slides small learned filters (say 3×3) across an image and responds wherever the local pattern matches. Stacking layers builds up from edges to textures to whole objects. On a log-mel spectrogram the "edges" are onsets, harmonics, and noise bursts; the "objects" are a dog bark's short harmonic stack, a jackhammer's periodic broadband pulses, or a siren's slow frequency sweep.

Two properties make CNNs a good fit:

  • Translation in time should not change the label: a bark at 0.5 s is the same class as a bark at 3 s. Convolution plus global pooling gives you that for free.
  • Local structure: nearby time frames and nearby mel bands are strongly related, exactly what small filters exploit.

One property does not carry over from photos: shifting a pattern up in frequency changes what it is. A 200 Hz hum and a 2 kHz whine are different sounds. CNNs still work, because deeper layers and the final classifier learn where in frequency things are, but this is why we never use vertical flips or large vertical shifts as augmentation.

Convolutions on spectrograms

Input shape for a batch is (batch, channels=1, n_mels, frames). A Conv2d(1, 16, kernel_size=3, padding=1) layer outputs (batch, 16, n_mels, frames): 16 feature maps, each the response to one learned 3×3 pattern. Strides of 2 halve both spatial axes, so after four stride-2 stages a 64×201 input is about 4×13. An AdaptiveAvgPool2d(1) then averages each feature map to one number, giving a fixed-length vector no matter how long the clip was, and a linear layer maps it to class logits.

The cost of a standard convolution with a \(k \times k\) kernel, \(C_{\text{in}}\) inputs and \(C_{\text{out}}\) outputs on an \(H \times W\) map is

\[ \text{params} = k^2 C_{\text{in}} C_{\text{out}}, \qquad \text{MACs} = k^2 C_{\text{in}} C_{\text{out}} H W. \]

MACs (multiply-accumulates) are the unit of compute that determines latency on small devices.

Depthwise-separable convolutions

MobileNets replace each standard convolution with two cheaper ones:

  1. A depthwise 3×3 convolution that filters each channel separately (groups=C_in): \(k^2 C_{\text{in}}\) parameters.
  2. A pointwise 1×1 convolution that mixes channels: \(C_{\text{in}} C_{\text{out}}\) parameters.

The ratio of cost to a standard convolution is \(\frac{1}{C_{\text{out}}} + \frac{1}{k^2}\). With \(k = 3\) and 64 output channels that is about 0.13, roughly 8× fewer parameters and MACs for a small drop in accuracy. This is the main trick behind every edge audio model you will read about.

A tiny audio CNN

A reasonable Module 1 starting point: about 18,000 parameters, 72 KB in float32 and about 18 KB in int8. That fits comfortably in an ESP32's memory.

import torch
import torch.nn as nn

class DSConv(nn.Module):
    """Depthwise-separable conv: per-channel 3x3, then 1x1 to mix channels."""
    def __init__(self, c_in, c_out, stride=1):
        super().__init__()
        self.dw = nn.Conv2d(c_in, c_in, 3, stride=stride, padding=1, groups=c_in, bias=False)
        self.pw = nn.Conv2d(c_in, c_out, 1, bias=False)
        self.bn = nn.BatchNorm2d(c_out)
        self.act = nn.ReLU()

    def forward(self, x):
        return self.act(self.bn(self.pw(self.dw(x))))

class TinyAudioNet(nn.Module):
    def __init__(self, n_classes=10):
        super().__init__()
        self.stem = nn.Sequential(nn.Conv2d(1, 16, 3, stride=2, padding=1, bias=False),
                                  nn.BatchNorm2d(16), nn.ReLU())
        self.blocks = nn.Sequential(DSConv(16, 32, stride=2), DSConv(32, 64, stride=2),
                                    DSConv(64, 64), DSConv(64, 128, stride=2))
        self.pool = nn.AdaptiveAvgPool2d(1)
        self.head = nn.Linear(128, n_classes)

    def forward(self, x):                 # x: (batch, 1, n_mels, frames)
        x = self.blocks(self.stem(x))     # -> (batch, 128, 4, 13) for a 64 x 201 input
        return self.head(self.pool(x).flatten(1))   # -> (batch, n_classes)

model = TinyAudioNet()
print(sum(p.numel() for p in model.parameters()))   # 18474
  • bias=False before BatchNorm2d: batch norm has its own shift, so a conv bias is redundant. After training, batch norm can be folded into the conv weights for deployment, which quantization tools do automatically.
  • Stride-2 layers shrink the map early, which is where most of the compute savings come from.
  • ReLU (or ReLU6) quantizes well. Fancier activations like GELU or Swish are slower and harder to quantize on microcontrollers.

UrbanSound8K and its folds

UrbanSound8K (Salamon, Jacoby, and Bello, 2014) has 8,732 labelled clips of up to 4 seconds in 10 classes: air conditioner, car horn, children playing, dog bark, drilling, engine idling, gun shot, jackhammer, siren, and street music. It is licensed CC BY-NC 3.0, so we download it ourselves and never commit it.

Use the predefined folds. Never shuffle and re-split.

The clips are cut from a smaller number of longer Freesound recordings, so many clips are near-duplicates from the same recording. The dataset ships pre-split into 10 folds that keep each source recording within one fold. If you pool all clips and make a random 80/20 split, slices of the same recording land in train and test, and accuracy jumps by 10 to 20 points for reasons that have nothing to do with your model. The authors' standard protocol is 10-fold cross-validation over the given folds. For quick iteration in the lab: train on folds 1–8, validate on 9, test on 10, and run the full 10-fold evaluation for any number you report.

Other practical details: clips vary in length (pad or crop to 4 s), in sample rate and bit depth (resample), and in channel count (convert to mono). The salience column marks whether the sound is in the foreground or background; reporting accuracy separately for each is an interesting robustness result in itself.

The training loop

frontend = LogMel().to(device)                     # from Concept 3
model = TinyAudioNet().to(device)
opt = torch.optim.AdamW(model.parameters(), lr=3e-3, weight_decay=1e-2)
sched = torch.optim.lr_scheduler.OneCycleLR(opt, max_lr=3e-3, total_steps=epochs * len(train_loader))
loss_fn = nn.CrossEntropyLoss(label_smoothing=0.1)

for epoch in range(epochs):
    model.train()
    for wav, y in train_loader:                    # wav already augmented in the Dataset (Concept 4)
        x = normalise(frontend(wav.to(device)))    # (B, 1, 64, 201)
        x = spec_aug(x)                            # training only
        loss = loss_fn(model(x), y.to(device))
        opt.zero_grad()
        loss.backward()
        opt.step()
        sched.step()

    model.eval()
    with torch.no_grad():
        val_acc = evaluate(model, val_loader)      # no augmentation, fixed preprocessing
    save_if_best(model, val_acc)
  • model.train() versus model.eval() switches batch norm between batch and running statistics. Forgetting eval() gives noisy, batch-size-dependent validation numbers.
  • Select checkpoints on the validation fold, never on the test fold.
  • Log everything: config, seed, git commit, and metrics, so any number in a slide can be reproduced. A plain CSV per run is fine; Weights & Biases or TensorBoard are nicer.
  • Start small: overfit a batch of 32 clips to near 100% training accuracy before training on everything. If you cannot, there is a bug.

Pretrained audio models

You do not always train from scratch. Large models pretrained on AudioSet (2 million YouTube clips, 527 classes) give strong embeddings and strong teachers:

  • PANNs (Kong et al., 2020): CNN14 and the much smaller MobileNetV1/V2 variants. Easy to use, great baselines.
  • YAMNet: a MobileNetV1 trained on AudioSet, the standard "small but pretrained" reference.
  • AST, BEATs, and similar transformers: higher accuracy, far too large for microcontrollers, useful as teachers for knowledge distillation into a tiny student.

For Module 1 a strong recipe is: train the tiny CNN from scratch as a baseline, then distil from a pretrained teacher and see how much of the gap closes. For Module 2 a pretrained encoder gives better clusters to start from.

Where this shows up in the lab

  • Module 1, /models/edge_audio: this is the model you compress in Concept 7.
  • Module 2, /training: the student audio encoder is a CNN like this one, retrained each generation on pseudo-labels.
  • Module 3: an optional classifier tells you what the localised source is, needed for the "classification accuracy across visible versus occluded" benchmark.

Check your understanding

Q1.How many parameters does a standard 3×3 conv from 32 to 64 channels have (no bias)? And a depthwise-separable one?

Standard: \(9 \times 32 \times 64 = 18{,}432\). Depthwise-separable: \(9 \times 32 + 32 \times 64 = 288 + 2048 = 2{,}336\). About 7.9× fewer.

Q2.Why does global average pooling make the model work for clips of different lengths?

It averages each feature map over all time and frequency positions, giving one number per channel whatever the map size. The linear head always sees a vector of length 128.

Q3.A teammate reports 97% on UrbanSound8K with a 20k-parameter model. What is the first question to ask?

"Did you use the official folds?" Random splits leak near-duplicate slices between train and test. Published 10-fold results for small models are usually in the 70s to low 80s.

Q4.Why is vertical flipping a bad augmentation for spectrograms?

It turns low frequencies into high ones, creating sounds that do not exist and may belong to another class. Frequency position carries meaning, unlike the vertical position of a cat in a photo.

Common mistakes

  • Random splits on UrbanSound8K, the most common way to report a meaningless number.
  • Tuning on the test fold, even informally ("let me check test after this change").
  • Forgetting model.eval() and torch.no_grad() during evaluation.
  • Augmenting validation data, so validation accuracy is noisy and checkpoint selection is random.
  • Mismatched front ends between the training script and the export script.
  • Reporting one run. Small models trained on small data vary by a point or two between seeds; report mean and spread over at least three.
