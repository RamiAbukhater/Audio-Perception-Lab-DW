Evaluation and experimental rigor

Every module ends in an evaluation suite: accuracy versus SNR in Module 1, convergence over pseudo-label generations in Module 2, angular error on visible versus occluded sources in Module 3. A research result is only as good as the measurement behind it. This page covers the metrics we use, the traps that inflate them, and how to report numbers other people can trust.

The big idea

An evaluation answers one question: how well will this work on data it has never seen, under the conditions we care about? Three things must hold for the answer to mean anything:

  1. The test data is truly unseen: not used for training, not used for choosing hyperparameters, and not a near-copy of anything that was.
  2. The metric matches the question: accuracy for balanced classes, macro-F1 when some classes are rare, angular error for directions.
  3. The number comes with its uncertainty: how much it moves across seeds, folds, or recordings.

Splits and leakage

Use three disjoint sets: train (fit weights), validation (choose hyperparameters, epochs, thresholds), and test (report once, at the end). Leakage is anything that lets test information influence the model. Audio is especially prone to it, because one long recording is usually cut into many clips:

  • Recording-level leakage: clips from the same source recording, room, or session in both train and test. Split by recording or session, not by clip. (UrbanSound8K's folds do this for you; your own Module 2 and Module 3 recordings will not.)
  • Augmentation leakage: the same noise or RIR files used in training augmentation and in the robustness test.
  • Preprocessing leakage: normalisation statistics or cluster centroids fitted on all data.
  • Selection leakage: looking at test results while iterating. The fix is discipline, not code.

For Module 2 and Module 3, where you record your own data, decide the split before recording: for example, sessions on Mondays and Tuesdays are training, Wednesday is validation, Thursday is test; or room A is train and room B is test (which also measures generalisation to new rooms).

Classification metrics

  • Accuracy: fraction correct. Fine when classes are roughly balanced, as in UrbanSound8K (mostly).
  • Per-class precision and recall: of the clips the model called "siren", what fraction were sirens (precision); of the real sirens, what fraction did it find (recall).
  • F1 is their harmonic mean; macro-F1 averages F1 over classes equally, so rare classes count as much as common ones. Use it for Module 2, where indoor classes like "doorbell" are rare.
  • Confusion matrix: rows are true classes, columns are predictions. It tells you which mistakes happen (air conditioner vs engine idling is the classic UrbanSound8K confusion). Always look at it.
from sklearn.metrics import accuracy_score, f1_score, confusion_matrix, classification_report

acc = accuracy_score(y_true, y_pred)
macro_f1 = f1_score(y_true, y_pred, average="macro")
cm = confusion_matrix(y_true, y_pred, normalize="true")    # each row sums to 1
print(classification_report(y_true, y_pred, target_names=CLASSES, digits=3))

Degradation curves

Module 1's headline figure is accuracy versus SNR: one line per model (float32 baseline, int8, pruned, each with and without noise augmentation), SNR on the x-axis from −10 dB to clean. The same pattern works for any stressor: RT60 on the x-axis for reverberation, gain in dB for level drops.

Summarise a curve with one number when you need to rank models: for example, accuracy at 0 dB, or the SNR at which accuracy falls to half its clean value.

Angular error

Module 3 measures how far the estimated direction is from the true one. Angles wrap around: 350° and 10° are 20° apart, not 340°. Always wrap the difference into \([-180°, 180°)\):

import numpy as np

def angular_error_deg(pred, true):
    """Absolute azimuth error in degrees, handling wrap-around."""
    d = (pred - true + 180) % 360 - 180
    return np.abs(d)

angular_error_deg(np.array([350, 10, 180]), np.array([10, 350, -180]))   # -> [20, 20, 0]

For full 3-D directions (azimuth and elevation), convert both to unit vectors and use the great-circle angle: \(\arccos(\hat u \cdot \hat v)\), with the dot product clipped to \([-1, 1]\). Report the median and the fraction within a tolerance (for example within 10° and within 20°), not just the mean, because a few reflections pointing the wrong way can dominate the mean.

Seeds, variance, and baselines

  • Seeds. Fix them (torch.manual_seed, numpy, random) so runs are repeatable, then run at least three seeds and report mean ± standard deviation. A 0.8-point improvement inside a 1.5-point seed spread is not an improvement.
  • Folds. On UrbanSound8K, cross-validation across the 10 folds gives you a spread for free.
  • Baselines. Every result needs something to beat: majority class, an SVM on mean MFCCs, the uncompressed model, or (for Module 3) plain GCC-PHAT without the physics layer. A fancy method that does not beat a simple baseline is a finding too; report it.
  • Ablations. When a pipeline has several parts (Module 3's line-of-sight check, occlusion filter, and reflection mapping), remove one at a time to show what each contributes.

Reporting checklist

  1. Data: which dataset, which split, how many clips per class, and how the split prevents leakage.
  2. Front end and model: every parameter needed to rebuild them, or a link to the config file and commit.
  3. Training: optimiser, schedule, epochs, augmentation, and seeds.
  4. Metric: exact definition, with mean ± std over seeds or folds.
  5. Baselines and ablations alongside the main result.
  6. For edge results: hardware or simulator, batch size 1, warm-up runs, and how latency and memory were measured (Concept 7).
  7. Failure cases: a few examples the model gets wrong, ideally with audio.

Check your understanding

Q1.You record Module 2 data for two weeks, then shuffle all 10-second windows and split 80/20. Why is the test accuracy too optimistic?

Neighbouring windows share the same events, the same background, and the same day's conditions. Many test windows are near-copies of training windows. Split by day or session instead.

Q2.A model predicts "dog bark" for everything in a dataset that is 60% dog barks. What are its accuracy and macro-F1 over, say, 5 classes?

Accuracy is 60%. Macro-F1 is low: the dog-bark class has F1 = 2(0.6·1)/(0.6+1) = 0.75 and the other four have 0, so macro-F1 = 0.15. Macro-F1 exposes the model; accuracy hides it.

Q3.Predicted azimuth −175°, true azimuth 170°. What is the error?

\((-175 - 170 + 180) \bmod 360 - 180 = (-165 \bmod 360) - 180 = 195 - 180 = 15°\).

Q4.Why report the median angular error alongside the mean?

Localization errors are heavy-tailed: most estimates are close, and a few lock onto a reflection 90° or more away. The mean mixes both behaviours; the median and "within 10°" rate describe typical performance, and the tail can be reported separately.

Common mistakes

  • Splitting by clip instead of by recording, session, or room.
  • Choosing the epoch or threshold on the test set.
  • Subtracting angles without wrapping.
  • One seed, no error bars, and a conclusion drawn from a difference smaller than the noise.
  • No baseline, so nobody can tell whether 78% is good.
  • Different test sets for different models, for example re-sampling noise for each model's robustness test. Generate the stressed test set once, save it, and reuse it.
